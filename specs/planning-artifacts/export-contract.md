# Export Contract Register

Canonical, enumerable register of the public export surface of `@vilnacrm/ui-toolkit`: one row per
module directory under `src/components/`, the value exports and type exports the package barrel
publishes for it, and — for a module deliberately kept off the surface — the reason and its
tracking ref.

- **Purpose** — satisfy `epics.md` Story 5.3 acceptance 3 (release-review evidence for the export
  surface, `epics.md:705-726`) from a single surface, so a reviewer can answer "is this module
  exported, and if not, why not?" without reading `src/components/index.ts` or git history.
  Story 5.4 consumes this register instead of re-deriving the barrel.
- **Owner** — Component Lead / Frontend Team (`prd.md:135`).
- **Governing requirements** — `prd.md` FR-07 acceptance 2 ("Exceptions are documented with
  rationale", `prd.md:221`); `epics.md` Story 5.3 "Export Contract and Entry Point Integrity"
  (`epics.md:705-726`); issue [#33](https://github.com/VilnaCRM-Org/ui-toolkit/issues/33).
- **Generated by hand, enforced by machine** — every row below is written by hand from the source
  tree, and `tests/unit/export-contract-integrity.test.ts` re-derives the same facts from the
  filesystem and from `src/components/index.ts` and fails the unit suite when this file and the
  code disagree. Edit this file and that guard together.

The rules this file instantiates are stated once in
`specs/implementation-artifacts/5-3-export-contract-and-entry-point-integrity.md`
("The export contract") and quoted verbatim under [Rules](#rules) below.

## Scope

A row covers every directory under `src/components/` that owns a component or module entry point —
`index.tsx` for a component, `index.ts` for a token/theme or shared-implementation module. Non-
directory entries of `src/components/` are out of scope and carry no row: `index.ts` (the barrel
itself), `fonts.css` (a stylesheet, see `DEV-43`) and `types.d.ts` (an ambient declaration file).

**Absent from this register is not a legal state.** A directory that owns an entry point and has no
row here is a drift-guard failure, not a silent omission: `tests/unit/export-contract-integrity.test.ts`
reads `src/components/` from disk and fails when a directory has neither an `exported` row nor an
`internal` row with a reason. A new component that is neither exported nor excepted therefore fails
CI rather than reaching review as a finding. The failure is closed by exporting the module or by
writing its `internal` row with a reason and a tracking ref — never by deleting the directory from
the guard's view.

## Rules

Quoted verbatim from
`specs/implementation-artifacts/5-3-export-contract-and-entry-point-integrity.md`, so the two files
cannot drift:

> - **R1 — value export.** Every directory under `src/components/` that owns a component entry point
>   (`index.tsx`) is re-exported by name from `src/components/index.ts`, unless it is listed as a
>   documented exception in the register.
> - **R2 — props type export.** Every publicly exported component publicly exports its props type
>   under the `Ui<Name>Props` name the component uses.
> - **R3 — reachable types.** Every type a consumer must be able to **name** in order to satisfy
>   R2 — an option/item shape, a union a prop accepts, a callback signature — is publicly exported
>   too. A type that only appears in an internal child's signature (`CardContentProps`,
>   `SkeletonTabsProps`, `SkeletonTableColumnSlot`, `SkeletonTextLine`, `ImageList`) is **not**
>   public, and the register says so.
> - **R4 — exceptions are traceable.** A module that is deliberately not exported carries a reason
>   and a tracking ref in the register. "Not exported" and "forgotten" must not be distinguishable
>   only by reading git history.
> - **R5 — enforcement.** R1-R4 are enforced by `tests/unit/export-contract-integrity.test.ts`, which
>   reads the filesystem and the register rather than a hand-maintained list, so a new component that
>   is neither exported nor excepted fails CI.

## Exceptions

The four `internal` rows above, in full. Each is an R4 exception: not exported, on purpose, with
the evidence written down.

### `app-theme`

`src/components/app-theme/index.ts` is a composed MUI theme — `createTheme` over the
`ui-breakpoints` and `ui-color-theme` modules plus a `MuiContainer` `styleOverrides` block. It owns
no component, so R1 does not reach it: there is no `index.tsx` and no rendered output to publish.
It is also, verified against the tree, consumed by nothing in `src/` — the only reference anywhere
in the repository is its own suite `tests/unit/app-theme.test.ts`. That is a stronger statement
than "internal shared implementation": the module is currently dead weight behind the barrel rather
than a dependency of the exported components. It is nonetheless kept, not deleted, because its
`MuiContainer` override is one half of the duplicated container sizing recorded as `DEV-40`
(`specs/planning-artifacts/deviation-ledger.md`), whose ruling — canonical owner is
`src/components/ui-container/styles.ts` — is a `deferred-tracked` follow-up rather than this
story's to execute. Exporting a theme that no toolkit component applies would publish an
unsupported second theming entry point. Tracking ref: `DEV-40`, Story 5.3 (#33).

### `field-controls`

`src/components/field-controls/index.ts` is the shared field-implementation barrel: the outlined
field theme, the shared `Glyph` and `ChevronDownGlyph`, `FieldLabel`, the ghost-completion overlay
and its helpers, `createFieldRenderInput`, `createFieldOptionRenderer`, `useListboxSlotProps`,
`useFieldAccessibilityWarnings` and the `srOnlySx` helper. It exports no component and has no
`index.tsx`, so R1 does not apply. Verified against the tree, it is imported by 15 sibling modules
— `ui-action-icon-bar`, `ui-calendar-multi-select`, `ui-file-upload-input`, `ui-filter-chip`,
`ui-item-row`, `ui-multi-select`, `ui-notification-badge`, `ui-pagination`, `ui-pin-input`,
`ui-profile-select-card`, `ui-radio-group`, `ui-search-input`, `ui-select-with-search`,
`ui-skeletons` and `ui-status-badge` — all of which are themselves either exported or internal by
their own ruling. Its symbols are implementation details of those components' contracts (render
factories and slot props keyed to MUI internals), so publishing them would freeze MUI-coupled
internals into the package's public API. It already carries an `internal`-flagged row in
`specs/planning-artifacts/component-provenance.md` for the same reason. Tracking ref: Story 5.3
(#33).

### `ui-card-item`

Ruled by Story 5.3 in
`specs/implementation-artifacts/5-3-export-contract-and-entry-point-integrity.md`, section
"Rulings" → "`ui-card-item` — internal, not a public deliverable (closes `DEV-42`)". Story 5.1
recorded the module as an export-surface inconsistency ("ships stories, unit tests and committed
visual baselines but is not exported"), and Story 5.2 ruled the standalone module canonical over
`src/components/ui-card-list/ui-card-item.tsx`, deferring the export decision here. The evidence
collected does not support exporting it:

- **No runtime consumer.** `src/components/ui-card-list/card-grid.tsx:6` and
  `src/components/ui-card-list/card-swiper.tsx:8` — the only two call sites in the repository —
  both import `./ui-card-item`, the in-list copy. `src/components/ui-card-item/index.tsx` is
  imported by nothing outside its own unit test.
- **The two are not interchangeable.** `src/components/ui-card-item/card-content.tsx` hardcodes the
  marketing site's "Integrate **services**" tooltip — a fixed `<Trans>` tree plus
  `ServicesHoverCard` — while `src/components/ui-card-list/card-content.tsx` is generic, driven by
  `item.tooltipTitle` / `item.tooltipLabel` and accepting `ReactNode` title and text.
- **Its stories and baselines are not its own.**
  `src/components/ui-card-item/card-item.stories.tsx` renders `UiCardList`, so the two baselines
  registered under `UiComponents/UiCardItem` in `tests/visual/stories.json` are `UiCardList`
  screenshots.

Exporting the module would publish hardcoded site copy under a generic name and add a second
`UiCardItem` contract to the package, so it stays internal; its public-facing surface is
`UiCardList`. Its `types.ts` and `constants.ts` remain consumed by `ui-card-list` and by the story
file, which is why the module cannot simply be deleted here. De-duplicating the two
implementations and renaming the mislabelled story file are behaviour-affecting changes to a
component with committed visual baselines and are handed off in the story artifact. Tracking ref:
`DEV-42` (`specs/planning-artifacts/deviation-ledger.md`), Story 5.3 (#33).

### `ui-skeletons`

`src/components/ui-skeletons/index.ts` is the shared skeleton barrel: the shimmer animation and
base styles (`base.ts`), the count constants (`counts.ts`) and `ComposedSkeleton`
(`src/components/ui-skeletons/composed.tsx`), the shared accessibility shell that supplies the
`aria-busy` container and its visually-hidden status text to the eleven skeleton primitives and to
`AuthSkeleton`. It owns no `index.tsx` and paints no board element of its own: every skeleton a
consumer needs is already published as its own `UiSkeleton*` export, and the shell is the private
mechanism behind them. Story 5.1 (`board-coverage-checklist.md`, "Hand-offs recorded here") and
Story 5.2 both flagged that this story's export sweep must not read `ComposedSkeleton` as a missing
export; this row, and the matching entry in the drift guard's exception list, record the ruling so
it survives independently of either prior artifact. Its `role`-free markup ruling is separately
recorded as `DEV-14`. Tracking ref: Story 5.3 (#33).

## Entry-point chain

Read from the repository, not from documentation, so the register can be checked against the tree:

1. **Package entry.** `src/index.ts` is a single line — `export * from './components';` — so the
   package's whole surface is `src/components/index.ts`, the barrel the register describes. There
   is no second entry point and no deep-import path a consumer may rely on.
2. **Barrel.** `src/components/index.ts` opens with `import './fonts.css';` (the side-effect import
   recorded as `DEV-43`) and then re-exports the value and type surface enumerated above.
3. **Published fields.** `package.json` declares `"main": "./build/index.mjs"`,
   `"module": "./build/index.mjs"` and `"types": "./build/index.d.ts"`; the `exports` map is
   `"."` → `{ "types": "./build/index.d.ts", "import": "./build/index.mjs" }` plus
   `"./styles.css"` → `"./build/index.css"`. `"files": ["build"]` means the published tarball
   carries the `build/` directory only, so `src/` is not reachable from an installed package and a
   type that is not re-exported by the barrel is genuinely unnameable by a consumer — which is what
   makes R2/R3 a consumability rule rather than a style preference. `"sideEffects": ["**/*.css"]`
   keeps the font stylesheet from being tree-shaken away.
4. **Runtime artifact.** `make build` runs `node ./build.config.mjs`, which emits `build/index.mjs`
   and `build/index.css` (the `./styles.css` subpath) alongside the font files.
5. **Type artifact.** esbuild emits no declarations, so `build.config.mjs` runs
   `tsc -p tsconfig.dts.json` into a freshly cleaned `temp/dts` and then invokes API Extractor;
   `make generate-ts-doc` runs the same extractor step on its own (`api-extractor run --local
--verbose`). Either path reads `api-extractor.json`, whose `mainEntryPointFilePath` is
   `<projectFolder>/temp/dts/components/index.d.ts` and whose
   `dtsRollup.untrimmedFilePath` is `<projectFolder>/build/index.d.ts` — the exact file
   `package.json` `types` and `exports["."].types` name. The rollup's entry point is the barrel, so
   a type that this register lists as public reaches consumers only because
   `src/components/index.ts` re-exports it; `build.config.mjs` additionally fails the build if any
   `@/*` path alias survives into the rollup.
